# JARVIS 项目计划

> Authority：Active
> Maturity：当前 M0 方向为 Confirmed；M1–M4 路线为 Proposed
> Status：M0 / High-level Architecture
> Canonical for：项目当前位置、阶段顺序、退出条件与当前下一步
> Updated：2026-07-24

## 1. 当前决定与候选路线

项目已经确认了动机、总体解决方向和基础技术可行性，但核心模块的合理性与边界尚未逐一讨论。如果此时直接实现 Demo，代码会固化未经确认的组织假设；如果继续无边界扩写细节，又会重复当前的长链迷失。

因此，当前已确认的动作是先完成 high-level 模块讨论。完成后怎样分阶段验证，先保留为一条可调整的建议路线：

```text
[Confirmed] M0 High-level Architecture
→ [Proposed] M1 GPT-only Demo
→ [Proposed] M2 Workflow Validation
→ [Proposed] M3 External Model Integration
→ [Proposed] M4 Open-source Release
```

这条候选路线的逻辑是：M0 决定系统应怎样工作；M1 用最少变量证明机制能够运行；M2 检查它在不同任务和故障下是否仍然有效；M3 再选择并验证外部模型接入方式；M4 把被证据支持的部分整理为他人可安装和复现的产品。M0 完成时需要重新审视 M1–M4，而不是让今天的建议自动升级为执行承诺。

## 2. 里程碑与依赖

| 里程碑 | 成熟度 | 要回答的问题 | 候选退出条件 |
|---|---|---|---|
| M0：High-level Architecture | Current / Confirmed | 四个核心模块为什么存在、如何衔接、边界在哪里？ | 四个模块形成已确认的 high-level 决定，并通过跨模块一致性检查 |
| M1：GPT-only Demo | Proposed | Codex 原生 Subagents 能否跑通一条可追踪的端到端任务链？ | Demo 的目标、角色、产物、验收和人工介入点明确，完整闭环至少成功运行一次 |
| M2：Workflow Validation | Proposed | 这套流程是否稳定，而非只在一个样例上成立？ | 多类真实任务和受控故障能够验证可靠性、定位能力与人工负担 |
| M3：External Model Integration | Proposed | 外部旗舰模型能否在质量达标的前提下降低总成本或提供独立价值？ | 选定兼容接入方式，并在同一任务协议下完成受控比较 |
| M4：Open-source Release | Proposed | 朋友能否从干净仓库理解、安装、运行和验证项目？ | 安装入口、文档、示例、测试、安全与许可检查全部通过 |

后一个里程碑原则上使用前一个里程碑的证据作为输入；是否严格串行、是否合并阶段，要在 M0 收口时重新决定。模型价格表、动态权重和淘汰机制不阻塞当前架构讨论。

## 3. 我们在哪里

### 已完成

- 明确监督两难和项目目标；
- 确认采用公司式分工与制衡来组织多 Agent；
- 确认 Codex 原生 GPT Subagents 可以作为第一阶段技术基础；
- 确认不能把 DeepSeek 等外部模型直接假定为当前原生 Subagent；具体接入方式仍未决定；
- 建立权威文档与历史提案的分层规则。

### 正在进行

M0：按依赖顺序完成四个核心模块的 high-level 讨论。

```text
治理与决策          ← 下一项
→ 任务组织与执行
→ 验证与责任追踪
→ 模型与资源管理
→ 跨模块一致性检查
```

治理先行的原因是：只有先决定用户与 Agent分别拥有什么权力，后续才能判断哪些工作可以自动拆分、执行、返工或升级。

### 尚未开始

- 不设计或实现 Demo 命令、数据结构和状态机；
- 不冻结 Planner、Executor、Reviewer 的固定人数；
- 不冻结 GPT 模型档位或推理强度；
- 不调用 DeepSeek、Kimi、GLM 等外部模型；
- 不实现动态路由、权重或淘汰；
- 不将尚未验证的流程固化为 Skill 或插件。

## 4. M0 的讨论方式

每个模块使用同一个最小结构，避免讨论再次散开：

```text
模块要解决的问题
→ 与前后模块的边界
→ 输入、输出和控制点
→ 正常路径与升级路径
→ 需要 Demo 验证的假设
→ Confirmed / Proposed / Open
```

完成一个模块后，只把明确接受的 high-level 结论同步到 [`ARCHITECTURE.md`](ARCHITECTURE.md)；候选细节保留为 `Proposed`，不提前扩写实现规格。

## 5. 进入 Demo 设计的门槛

满足以下条件后，M0 才结束：

1. 四个模块都能说明自己的职责和相邻边界；
2. 一次任务从目标进入到结果裁决的主数据流完整；
3. 人工介入点、验证反馈和故障归因之间不存在明显断点；
4. GPT-only Demo 只需要验证少量明确假设，而不是替架构讨论补洞；
5. 用户能够从一页总览判断目标、当前位置和下一阶段距离。

达到门槛后再在 `docs/designs/` 中创建新的活动 Demo 设计文档：先标为 `Proposed`，获准后转为 `Confirmed` 并冻结范围，验证完成后转为 `Verified` 并链接证据。早期详细方案已经保存在 [`archive/2026-07-24-initial-design/`](archive/2026-07-24-initial-design/)，届时可以选择性吸收，但不会自动恢复为当前决定。

## 6. 当前下一步

下一次架构讨论只处理“治理与决策”：

- 用户必须保留哪些决定；
- 主 Agent可以自主决定哪些事项；
- 专业 Agent的权限边界是什么；
- 哪些事件必须暂停流程并升级；
- 怎样避免人工介入重新退化成逐步检查。

这组决定完成后，才进入“任务组织与执行”，因为调度策略必须在已确认的治理边界内设计。
