# JARVIS 架构总览

> Authority：Active
> Maturity：总体方向为 Confirmed；模块细节为 Open
> Scope：只记录已确认的总体方向、技术边界和待讨论模块
> Canonical for：项目如何解决长链迷失，以及核心模块之间的关系
> Updated：2026-07-24

## 1. Overview：从监督困境到组织架构

项目要解决的是一个监督两难：人逐步检查虽然可靠，却会成为工作流瓶颈；人完全放手虽然流畅，长链末端一旦出错，又难以定位最早偏差。

因此，我们不把答案定义为“启动更多 Agent”，而是借鉴公司运行中的分工、交接、制衡和问责，把长任务组织成可追踪的协作链。用户负责目标、风险边界和最终裁决；主 Agent负责理解任务、组织资源和处理异常；专业 Agent承担规划、执行、研究或审查；测试与证据提供不依赖模型共识的客观反馈。

这套方案成立的关键不是角色名称，而是每次交接都有明确的任务边界、产物和验收依据。只有这样，人才能把注意力上移，同时仍能在发生问题时找到责任链中的最早偏差。

## 2. 解决原理：把一次长委托变成可观察的控制循环

长链之所以容易失控，是因为目标理解、方案选择、代码修改和结果判断都被压进同一段上下文。系统将它拆成一个带反馈的控制循环：

```text
用户定义目标与边界
→ 主 Agent形成任务契约并组织工作
→ 专业 Agent在受控上下文中产生产物
→ 客观检查与独立审查验证结果
→ 主 Agent根据证据接受、返工或升级
→ 运行记录反向支持后续资源选择
```

前半段解决“谁做什么”，验证环节解决“凭什么相信”，反馈环节解决“出错后如何定位并改进”。这三部分缺一不可：只有分工而没有验证，会把错误藏进更长的委派链；只有验证而没有任务边界，仍然无法判断问题源自规划还是实现。

## 3. 技术基础：原生 Subagent 与外部模型分层

总体机制在 Codex 中具有可实现基础，但原生 Subagent 和外部模型的兼容程度需要分开判断。

```text
用户
└── Codex 主 Agent
    ├── 原生 Codex Subagents：当前可直接验证
    └── 外部供应商模型：接入形态尚未决定
```

Codex 原生支持主 Agent创建并管理专门化 Subagent，也支持角色级模型与推理强度配置，因此 GPT-only 协作可以直接用现有能力验证。[Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)

跨供应商部分目前只确认兼容性边界：Codex 当前自定义 Provider 使用 Responses 协议，而 DeepSeek 官方接口当前主要提供 Chat Completions 与 Anthropic 兼容接口。因此不能把 `deepseek-v4-pro` 当作当前原生 Subagent 的普通模型名直接传入，也不能据此假定同一主 Agent会话已经支持混合供应商调度。[Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference) · [DeepSeek API](https://api-docs.deepseek.com/api/create-chat-completion)

外部接入可以有多种候选形态：Responses 转译 Gateway、MCP/CLI Adapter、独立 Codex 进程，或自带工具循环的 Worker。它们在权限、上下文、工具执行和维护成本上不同，目前均为 `Proposed`，尚未选型。如果最终希望外部模型像 Executor 一样读取仓库、修改文件并运行测试，所选方案必须承担工具循环、工作区隔离、重试和证据返回；一次普通 API 调用只能产生文本或补丁，不能自动获得这些能力。

因此，已确认的只是“先用原生 GPT Subagents 验证组织机制”和“外部模型需要另行验证兼容路径”，不是某一种 Adapter/Worker 实现。

## 4. 核心模块：按依赖顺序逐一讨论

技术可行性只回答了“能不能搭起来”，还没有回答组织应该怎样运行。后续设计分成四个相互依赖的模块，并按以下顺序讨论：

```text
1. 治理与决策
   └── 决定谁拥有什么权力、何时需要人工介入
        ↓
2. 任务组织与执行
   └── 在治理边界内完成拆分、调度、交接和隔离
        ↓
3. 验证与责任追踪
   └── 判断结果是否可信，并定位最早偏差
        ↓
4. 模型与资源管理
   └── 根据任务需求和历史证据选择模型、人数与预算
        └──────────运行反馈回到治理和调度
```

### 4.1 治理与决策

这一模块先定义用户、主 Agent和专业 Agent的决策边界，以及升级、暂停和最终裁决的触发条件。它必须最先讨论，因为没有权力边界，后续的“自动调度”就可能越过用户真正想保留的控制点。

### 4.2 任务组织与执行

治理边界确定后，才能讨论任务如何形成契约、怎样拆分、哪些工作可以并行、上下文如何隔离，以及多个写入者如何避免冲突。这一模块把抽象职责转化为实际工作流。

### 4.3 验证与责任追踪

工作流形成后，还需要确定自动测试、独立 Reviewer、证据包和故障归因怎样协作。它既是交付门禁，也是后续判断“规划错了、实现错了还是验收错了”的数据来源。

### 4.4 模型与资源管理

只有知道每个岗位的职责和评价证据后，模型选择、推理强度、Subagent 数量、成本比较、动态权重和淘汰才有可靠基础。否则所谓动态用人只是模型印象或价格驱动的主观路由。

## 5. 当前共识与未决边界

### Confirmed

- 项目目标是减少人工微观监督，同时提高长链任务的可定位性。
- 解决方向是建立有职责边界、独立验证和升级机制的多 Agent 组织。
- 项目先使用 Codex 原生 GPT Subagents 验证协作机制。
- 不假定外部供应商模型可以原生混入当前 Subagent 运行时；具体接入形态仍待选型。
- 项目最终面向 GitHub 开源，但只发布整洁、可复现、可维护的资产。

### Open

- 用户与主 Agent分别保留哪些决定，人工介入由什么触发；
- Planner、Executor、Reviewer 等职责是否都需要独立实例，以及人数如何弹性变化；
- 任务契约、上下文交接、并行和写入隔离采用什么最小机制；
- 自动测试、独立审查、证据和故障归因怎样组合；
- 模型、推理强度、价格、动态权重和淘汰使用什么策略；
- 最终交付是 Skill、插件、外部 Worker，还是它们的组合。

这些问题在对应模块被明确接受之前，不得写成已冻结协议或直接驱动 Demo 实现。

## 6. 讨论如何转化为架构决定

每个模块的 high-level 讨论只需要产出五类信息：

1. 它解决什么问题；
2. 它与相邻模块的边界；
3. 关键输入、输出和控制点；
4. 正常路径、升级条件和主要失败模式；
5. 已确认决定与保留到 Demo 验证的假设。

四个模块完成后再进行一次跨模块一致性检查。只有控制权、数据流、验证反馈和资源选择能够连成闭环，项目才进入 GPT-only Demo 设计。
