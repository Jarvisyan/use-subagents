# Vibe Research Skills

> AI 的知识广度和组合能力使它能够快速提出并执行大量可能方案；同一优势也会把任务展开成巨大的搜索空间，使模型容易抓不住当前最关键的问题，或在规划、实现和写作中逐步偏离目标。Vibe Research Skills 通过少量稳定的 meta constraints 约束 AI 的搜索过程，把广泛能力收敛为聚焦、可靠且可由用户判断的推进。

当前实现覆盖两类高频工作：`solid-vibe-coding` 与 `experiment-layout` 支持研究实验迭代，`vibe-paper` 支持在方法和核心实验已经固定后规划、撰写和检查论文 Method。各模块先独立做到可靠，再逐步扩展到完整研究流程。

## 1. 设计动机：能力越强，搜索空间越大

AI 擅长调用广泛知识、组合不同方法并快速实现候选方案，但它面对的往往不是“会不会做”，而是“当前最应该做什么”。对于一个粗糙但 non-trivial 的研究 Idea，模型可以展开大量看似合理的实验方向、Backbone、设计变体和实现方式；如果缺少选择边界，它很容易投入低价值分支、混合多个改动，或在 Coding 阶段重新解释 Plan。

```text
知识与组合能力
  -> 大量合理候选
  -> 实验、实现和表达的搜索空间迅速膨胀
  -> 缺少边界时抓不住重点或逐步跑偏
```

这套 Skills 不试图预先规定正确答案，而是在搜索空间最容易失控的位置设置 meta constraints：规定当前应解决什么问题、哪些变量必须固定、实现阶段拥有什么自由度，以及哪些判断必须交还用户。目标不是限制 AI 的能力，而是让它的知识和执行能力持续指向当前最重要的任务。

## 2. 核心设计：约束搜索，而不是规定答案

这些 Skills 固定的不是模型品牌、Agent 数量或执行拓扑，而是跨任务稳定的搜索边界。AI 负责生成和执行候选方案，Skills 负责压缩搜索空间和约束自由度，用户在关键 gate 判断方向是否值得继续、Plan 是否合理以及实现是否可以提交测试。

```text
AI
  -> 生成和执行候选方案
Skills
  -> 收敛方向、固定实验语义、限制实现自由度
用户
  -> 接受 Plan、决定是否提交最终实现
```

在研究实验中，这套分工落实为：

```text
粗糙 Idea + 可用项目证据
  -> 对抗式选择下一项实验方向
  -> 对抗式确定 Backbone 并隔离一个目标改动
  -> [用户根据 Plan 报告决定是否继续]
  -> 在不重开实验选择的前提下实现 Plan
  -> 对抗式检查实现是否忠于 Plan
  -> [用户根据 Check 报告决定提交测试、修复、重规划或停止]
```

默认由主对话模型贯穿这一过程，持续持有用户目标、项目上下文、已接受的 Plan 和实现状态。Plan Challenger 与 Check Challenger 是两个先后启用的临时 subagent：前者攻击实验方向和设计中最可能导致无效探索的漏洞，后者在提交测试前核对实现是否越过 Plan 边界。对抗过程使用项目证据而不是纯粹意见竞争，并在形成共识或达到规定轮次后停止；未解决的异议交给用户。

## 3. `solid-vibe-coding`：工作流控制层

### Plan：选择下一项实验方向

面对粗糙 Idea 展开的巨大空间，Plan 不先罗列所有可能实验再逐个尝试，而是优先寻找否决性实验（Kill Criteria）或分支决策点（Fork in the Road）。前者在失败时能够停止一条无效路线，后者用结果在实质不同的路线之间做选择；二者都比在尚未确定的路径内调参更能减少后续搜索。

Plan Challenger 检查是否有更具决策价值的实验应该先做，以及当前提议能否否决低潜力路线或选出更值得推进的主干。它约束的是实验选择方式，不预先规定正确方向。

### Plan：确定 Backbone 与单因子设计

Backbone 不是默认已经确定的前置条件。Plan 需要先识别并论证本轮实验应使用的 Backbone；已有版本合适时继续使用，没有充分依据时则把 Backbone 选择本身提升为下一项关键实验。Backbone 一旦选定，在本轮比较中保持冻结。

随后只定义一个目标设计改动，并冻结与它无关的数据预处理、损失、训练超参数和评价协议。任何可能改变对照关系或涨跌归因的选择都必须在 Plan 中确定；Coding 阶段只保留不改变实验语义的实现自由度。这样做不是要求 Plan 规定所有代码细节，而是防止实验设计在实现过程中被悄悄重开。

### Coding 与 Check：实现 Plan，而不是继续设计实验

主模型在已接受的 Plan 内完成实现，可以处理 Plan 未规定的普通工程细节，但不能改变实验方向、选定的 Backbone、目标改动或冻结项。Check Challenger 在提交测试前比较 Plan 与实现：既检查 Plan 要求的改动是否完整、语义正确并进入预期执行路径，也检查未授权的实验相关改动是否出现。

Plan 内的实现 bug 可以集中修复并进行一次最终复查；任何需要新增实验选择或改变冻结项的修复都返回 Plan。Check 通过后，由用户决定提交测试、继续修复、重新规划或停止。Skill 不审计测试结果；量化结果由用户判断，并可作为下一轮规划的项目证据。

### Plan 与 Check 报告

两类报告都保留足够上下文、证据、主要异议和最终处置，使用户能够直接判断是否接受，而不必重新拼装对抗过程。聊天汇报压缩决策相关要点，文档保留审计和复现细节。

## 4. `experiment-layout`：实验信息架构层

AI 的执行能力还会快速产生大量脚本、配置和输出，使文件系统本身成为新的搜索空间。`experiment-layout` 把实验目录设计成面向用户判断的层级：打开根目录能看到按顺序编号的 Plans；打开一个 Plan 能看到它包含的编号子实验；打开一个子实验能立刻找到按局部编号对应的测试脚本和最终结果。

脚本与输出使用相同的 `Plan.子实验.测试` 身份，使用户可以沿编号直接对应。共同支持一个结论的测试留在同一个子实验；能够单独判断的测试拆成新的子实验。seed、variant、stage、retry 和 helper 留在所属实验内部。正式输出默认只保留判断 Plan 所需的最终数据，结果解释集中在 Plan 级报告；中间结果仅在复现判断或继续任务确有需要时保留。

Skill 不强制 `scripts/`、`outputs/`、`src/` 等具体名称。它约束的是用户路径：目录按 Plan 和子实验展开，而不是按 AI 的操作时间线或处理阶段展开；未来实验真正开始后才创建，避免提前生成空目录。

## 5. 两套 Skill 如何配合

```text
solid-vibe-coding
├── 方向：优先 Kill Criteria 或 Fork in the Road
├── 设计：论证 Backbone，并隔离一个目标改动
└── 实现：核对 Plan 与代码，提交测试前阻止偏航

experiment-layout
├── 为 Plan 和子实验建立稳定的两级编号
├── 让测试脚本与最终输出沿相同局部编号直接对应
└── 突出入口与最终结果，下沉或省略中间产物
```

通常由 `solid-vibe-coding` 把粗糙 Idea 推进到可提交测试的实现；当任务会产生持久实验脚本、输出和报告时，再组合使用 `experiment-layout`。前者约束认知与实现搜索空间，后者约束产物搜索空间，两者互不替代。

## 6. `vibe-paper`：本地论文写作层

写作同样会因 AI 可调用的信息和表达方式过多而失焦：内容边界不断扩张，创新点被背景淹没，结构也随生成过程漂移。`vibe-paper` 通过固定内容选择和读者路径来收敛写作搜索空间；它把论文按章节拆成可独立设计和迭代的工作流，当前只实现 Method，不把尚未验证的通用写作规则提前复制到 Introduction、Related Work 或 Experiments。

Method 工作流接收已经确定的方法、创新定位、实现和论文上下文，不重新决定研究贡献。它通过对抗 Plan 同时回答两个问题：Method 应选择哪些信息、分别解释到什么程度，才能突出创新并完整定义方法；这些内容应如何分解、排序和呈现，才能降低阅读成本并让读者无歧义地重建算法。用户接受 Plan 后，AI 逐块写作并进行最多三轮对抗检查，用户决定接受、重写、重规划或停止；所有块完成后再检查跨块一致性。

```text
固定方法、创新定位、实现与论文上下文
-> 对抗式规划 Method 的内容边界与读者路径
-> [用户决定是否接受 Method Plan]
-> 细化并撰写当前 block
-> 对抗式检查来源、Plan 与局部解释链的一致性
-> [用户决定接受、重写、重规划或停止]
-> 逐块推进，最后检查完整章节
```

`skill/vibe-paper/SKILL.md` 只负责自动触发和章节路由；Method 的完整规则保存在 `skill/vibe-paper/references/method.md`，触发后按需读取。后续每完成一个章节工作流，再增加对应 reference 和路由，不让顶层 Skill 膨胀成通用写作规则集合。

这个 Skill 面向本地论文写作环境。本仓库只保存和同步其源文件；云服务器不安装、不注册，也不在服务器的 `~/.codex` 中建立链接。

## 7. 源文件与同步边界

这个仓库现在是通用 Codex 配置的单一源。`AGENTS.md`、`skill/solid-vibe-coding/`、`skill/experiment-layout/` 与 `skill/vibe-paper/` 进入 Git，供不同机器同步；`solid-vibe-coding` 与 `experiment-layout` 可由服务器的 `~/.codex` 通过符号链接引用，`vibe-paper` 只在本地论文写作环境安装。

`integrations/` 与 `skill/cluster-routing/` 包含服务器专用的工具、路径和资源规则，因此保留在本地仓库目录中，但由 `.gitignore` 排除，不上传云端。外部模型或服务器工具仍可按本机配置显式使用，不成为这些通用 Skills 的依赖。

原 `multi-subagents` 原型已经由职责更单一的 `solid-vibe-coding` 与 `experiment-layout` 取代。通用 Skill 只保留跨任务稳定的 meta 约束；服务器环境和 provider 实现留在本地配置层。
